AI + developer experience case study

Preserving Design Intent with AI

A prototype for translating structured Figma output into ServiceNow-aware implementation guidance.

As our team moved more workflow experiences into ServiceNow, a recurring gap became clear: designers could define the intended experience in Figma, but engineers still had to interpret how that design should translate into ServiceNow components, patterns, and platform constraints.

The goal was not to let AI design the interface. It was to reduce the interpretation gap between design intent and platform implementation.

01The Problem
The Problem

A Figma design does not tell an engineer how to build the experience in ServiceNow.

The handoff contained the visual and interaction intent, but implementation still required engineers to interpret the design against a very different platform model: ServiceNow components, page frameworks, configuration options, design-system patterns, and technical constraints.

That translation was manual and inconsistent. Similar design elements could be implemented differently depending on who picked up the work, while platform limitations might not become visible until development had already begun.

The challenge was not converting pixels into code. It was making the translation logic explicit.
A

Component ambiguity

A Figma component could map directly, require configuration, use a reusable pattern, or have no native equivalent.

B

Platform context

The right implementation depended on the target surface—not simply on what the design looked like.

C

Hidden exceptions

Some decisions could be automated confidently; others required interpretation or explicit human judgment.

What engineers were interpreting manuallyDeep dive

For each design element, engineers had to determine the closest ServiceNow component or pattern, understand which properties and tokens carried over, identify where custom implementation might be required, and reconstruct the intended page hierarchy and behavior.

02The Exploration
The Exploration

Separate what can be known from what still requires judgment.

I treated the handoff as a classification problem rather than a code-generation problem. For each Figma element, the system needed to say not only what it thought the ServiceNow equivalent was, but how confident that mapping was and what kind of implementation it implied.

A

Native match

A direct ServiceNow component exists and can be used largely as-is.

B

Native + configuration

A native component exists, but properties, variants, or configuration are required.

C

Template / pattern

No single component is sufficient, but an approved combination can represent the intent.

D

Gap / not feasible

The system cannot make a reliable platform-native recommendation and surfaces the issue instead of inventing an answer.

Confidence was useful only if uncertainty remained visible.
A

Make the mapping visible

Each Figma instance was classified, paired with a ServiceNow recommendation, and accompanied by implementation guidance. The report exposed the reasoning instead of hiding it behind a generated result.

Responsibility boundaries

Rules, reasoning, and human review played different roles.

Deterministic rules

Known facts stay explicit.

Approved component mappings, known tokens, reusable patterns, and platform constraints.

Agent reasoning

Interpret what is not one-to-one.

Read hierarchy and intent, evaluate plausible implementation paths, classify feasibility, and explain recommendations.

Human judgment

Keep ambiguous choices visible.

Resolve unclear requirements, validate experience quality, approve exceptions, and decide when custom work is warranted.

The agent’s job was not to hide uncertainty. It was to make uncertainty actionable.
How the mapping model worked

The Figma export preserved multiple kinds of signals. Component instances were treated as primary implementation candidates, while frames helped establish structure and text nodes preserved content. This prevented the system from trying to map every visual element into a ServiceNow component.

03The Solution
The Solution

A platform-aware translation workflow

The prototype combined structured Figma output, an explicit mapping and classification layer, and ServiceNow-aware implementation logic. Together they turned a design export into guidance that engineers could inspect rather than blindly accept.

01

Export

Capture structured Figma information rather than a screenshot.

02

Analyze

Map components, classify feasibility, detect gaps, and preserve hierarchy.

03

Explain

Return ServiceNow-aware guidance, generated code, and build steps.

04

Review / Generate

Let a human inspect the recommendation before creating preview or page artifacts.

Then I moved the capability into the platform itself

SNOWY became the conversational layer over the translation engine.

The initial mapping engine proved the translation logic. The next step was to make that capability accessible where engineers were already working by implementing SNOWY as an AI agent inside ServiceNow.

The agent could analyze a Figma design, retrieve conversion history, explain the results conversationally, and initiate generation actions when appropriate.

The conversational layer did not replace the mapping engine. It made the capability easier to interrogate and act on.
Inside the agentDeep dive

The deployed agent separated distinct capabilities for analyzing a Figma design, retrieving prior conversion results, and generating a page. Keeping those tools distinct made the workflow easier to reason about and preserved human control over generation.

From recommendation to implementation artifact

Generation was scaffolding for review—not proof that the design was finished.

The prototype could go beyond classification and produce implementation scaffolding: generated markup, styles, client and server logic, build guidance, and—in supported cases—a page or widget that could be opened directly in ServiceNow for review.

The output was a starting point engineers could inspect, not an opaque final answer.
How far generation could go

Generated artifacts could include page structure and implementation code that accelerated setup, while unresolved mappings and platform-specific exceptions remained visible for review.

04The Impact
The Impact

The prototype validated the translation layer.

This was not a production deployment, so I would not measure its success by adoption or delivery metrics. What we validated was that structured design intent could be translated into platform-aware recommendations without collapsing everything into generic AI generation.

Mapping could be explicit

The system could distinguish direct matches from configuration needs, patterns, and unsupported cases.

Gaps could remain visible

Unsupported or ambiguous elements were surfaced instead of being silently approximated.

Guidance could become actionable

The output included implementation recommendations, generated code, and build steps engineers could inspect.

The capability could live inside ServiceNow

The mapping logic could be exposed through a native AI agent and connected to generation tools in the engineers’ working environment.

It also changed the conversation with Engineering

The prototype became a concrete engineering capability—not just a design experiment.

What began as a way to reduce handoff friction became a component library, mapping model, agent workflow, backlog, and a clear separation between work that could continue in the POC environment and work requiring production governance.

From prototype to engineering backlogDeep dive

The follow-on plan separated critical unblockers, component expansion, hardening, and eventual scale so engineering work could continue without treating the prototype as production-ready.

Execution under changing constraintsDeep dive

The prototype also had to survive changing ServiceNow environments, permissions, and agent setup. I documented the architecture and state carefully enough that the work could continue after migration and handoff rather than depending on one instance or one person.

What I learned

AI was most useful when it reduced ambiguity without pretending judgment had disappeared.

This work changed how I think about AI in design workflows. The most valuable part was not asking a model to produce more output. It was using AI to make an existing translation problem more explicit—what we know, what the platform allows, where interpretation is required, and where people still need to decide.

Reduce ambiguity. Preserve judgment.
