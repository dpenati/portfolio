Preserving Design Intent with AI

A prototype for translating structured Figma output into ServiceNow-aware implementation guidance.

As our team moved more workflow experiences into ServiceNow, a recurring gap became clear: designers could define the intended experience in Figma, but engineers still had to interpret how that design should translate into ServiceNow components, patterns, and platform constraints.

The goal was not to let AI design the interface. It was to reduce the interpretation gap between design intent and platform implementation.

01The Problem
The Problem

A Figma design does not tell an engineer how to build the experience in SN.

The handoff contains the visual and interaction intent, but implementation still requires engineers to interpret the design against a very different platform model: ServiceNow components, page frameworks, configuration options, design-system patterns, and technical constraints.

That translation is manual and inconsistent. Similar design elements can be implemented differently depending on who picks up the work, while platform limitations might not become visible until development has already begun.

A

Component ambiguity

A Figma component could map directly, require configuration, use a reusable pattern, or have no native equivalent.

B

Platform context

The right implementation depended on the target surface—not simply on what the design looked like.

C

Hidden exceptions

Some decisions could be automated confidently; others required interpretation or explicit human judgment.

The challenge was not converting pixels into code. It was making the translation logic explicit.
What engineers were interpreting manually

For each design element, engineers had to determine the closest ServiceNow component or pattern, understand which properties and tokens carried over, identify where custom implementation might be required, and reconstruct the intended page hierarchy and behavior.

02The Exploration
The Exploration

Separate what can be known from what still requires judgment.

I treated the handoff as a classification problem rather than a code-generation problem. For each Figma element, the system needed to say not only what it thought the ServiceNow equivalent was, but how confident that mapping was and what kind of implementation it implied.

A

Native match

A direct ServiceNow component exists and can be used largely as-is.

B

Native + configuration

A native component exists, but properties, variants, or configuration are required.

C

Template / pattern

No single component is sufficient, but an approved combination can represent the intent.

D

Gap / not feasible

The system cannot make a reliable platform-native recommendation and surfaces the issue instead of inventing an answer.

Confidence was useful only if uncertainty remained visible.

Make the mapping visible

Each Figma instance is classified, paired with a ServiceNow recommendation, and accompanied by implementation guidance. The report exposes the reasoning instead of hiding it behind a generated result.

Responsibility boundaries

Rules, reasoning, and human review played different roles.

Deterministic rules

Known facts stay explicit.

Approved component mappings, known tokens, reusable patterns, and platform constraints.

Agent reasoning

Interpret what is not one-to-one.

Read hierarchy and intent, evaluate plausible implementation paths, classify feasibility, and explain recommendations.

Human judgment

Keep ambiguous choices visible.

Resolve unclear requirements, validate experience quality, approve exceptions, and decide when custom work is warranted.

The agent’s job was not to hide uncertainty. It was to make uncertainty actionable.
How the mapping model worked

The Figma export preserved multiple kinds of signals. Component instances were treated as primary implementation candidates, while frames helped establish structure and text nodes preserved content. This prevented the system from trying to map every visual element into a ServiceNow component.

03The Solution
The Solution

From Figma intent to ServiceNow implementation

The prototype turned the translation logic into an end-to-end workflow: preserve structure from Figma, classify what ServiceNow can support, surface uncertainty, then generate artifacts only after the interpretation can be reviewed.

01

Export the design

Use Figma2Prompt to capture structured JSON instead of flattening the design into an image.

02

Run the engine

Paste the export into the MVP and select the target ServiceNow experience.

03

Classify the page

Map components and patterns, expose confidence, and identify unsupported elements.

04

Review the gaps

Surface what cannot be mapped reliably rather than silently approximating it.

05

Generate a preview

Create a structural preview so the interpretation can be checked before implementation.

06

Generate the page

Use the approved mappings to create ServiceNow implementation artifacts.

07

Inspect the result

Review the generated HTML, CSS, client logic, server logic, and resulting widget or page.

01–04

Preserve structure. Make the interpretation visible.

The workflow starts with structured Figma output, not a screenshot. Once the JSON enters the mapping engine, it moves into the classification logic shown in Exploration.

The important part was not that the system produced an answer. It was that engineers could see how it arrived there.
04–05

Surface gaps before generating anything.

Once unsupported and ambiguous mappings had been surfaced, the preview provided a low-cost checkpoint to validate whether the system had interpreted the Figma structure correctly before creating ServiceNow artifacts.

Uncertainty became something the team could review—not something the system quietly filled in.
Then I moved the capability into the platform itself

SNOWY became the conversational layer over the translation engine.

The mapping engine established the translation logic. I then implemented SNOWY inside ServiceNow so engineers could analyze a design, inspect results, retrieve prior conversions, and initiate generation without leaving the platform.

The conversational layer did not replace the mapping engine. It made the capability easier to interrogate and act on.
Inside the agent

The deployed agent exposed distinct tools for analyzing a Figma design, retrieving conversion history, and generating a page. Keeping those capabilities separate made the workflow easier to reason about and preserved human control over generation.

06–07

Generate the artifact—then inspect it.

With the approved mappings in place, the workflow could create ServiceNow implementation scaffolding: markup, styles, client and server logic, and—in supported cases—a working page or widget.

Generation was a starting point for review, not proof that the design had been implemented correctly.
Implementation detail

Generated artifacts could accelerate setup, while platform-specific exceptions and unresolved mappings remained available for review and correction.

04The Impact
The Impact

The prototype validated an end-to-end translation workflow.

This was not a production deployment, so I would not measure its success by adoption metrics. What we validated was the full path from structured Figma intent to inspectable ServiceNow implementation artifacts—while keeping uncertainty and human review visible throughout.

Intent stayed structured

The workflow preserved component, hierarchy, content, and styling signals rather than reducing the design to pixels.

Uncertainty stayed visible

Unsupported or ambiguous elements were surfaced before generation instead of being silently approximated.

Interpretation became actionable

Classification, guidance, preview, code, and build steps gave engineers concrete material to inspect and use.

The workflow reached the platform

The translation logic could be exposed through a native ServiceNow AI agent and connected to page-generation tools.

It also changed the conversation with Engineering

The prototype became a concrete engineering capability—not just a design experiment.

What began as a way to reduce handoff friction became a component library, mapping model, agent workflow, backlog, and a clear separation between work that could continue in the POC environment and work requiring production governance.

From prototype to engineering backlog

The follow-on plan separated critical unblockers, component expansion, hardening, and eventual scale so engineering work could continue without treating the prototype as production-ready.

Execution under changing constraints

The prototype also had to survive changing ServiceNow environments, permissions, and agent setup. I documented the architecture and state carefully enough that the work could continue after migration and handoff rather than depending on one instance or one person.

What I learned

AI helped to reduce uncertainty without removing human judgment.

This work changed how I think about AI in design workflows. The most valuable part was not asking a model to produce more output. It was using AI to make an existing translation problem more explicit—what we know, what the platform allows, where interpretation is required, and where people still need to decide.

Reduce ambiguity. Preserve judgment.
